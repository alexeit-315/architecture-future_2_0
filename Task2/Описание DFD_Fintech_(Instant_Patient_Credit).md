# Описание бизнес-сценария «Использование нового финтех-сервиса»

Для примера разработана data flow diagram для использован бизнес-процесса «Мгновенное финансирование пациента» (Instant Patient Credit).

### Детализированное пошаговое описание потоков данных

Шаг| Поток данных        | Источник -> Приёмник                     | Что происходит                                                                                                                                         | Механизм 
---|---------------------|------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------| --------
 1 | PaymentRequest      | Пользователь (портал) -> Медицина        | Пользователь выбирает оплату в рассрочку. Портал вызывает API медицинского приложения для создания счёта.                                              | REST API
 2 | TokenRequest        | Медицина -> Security & Compliance Layer  | Медицинское приложение вызывает сервис анонимизации для получения токена пользователя. Далее вместо ПдН передается и обрабатывается токен.             | REST API 
 3 | InvoiceCreated      | Медицина -> Message Queue                | После генерации счёта создаётся CDC-событие (invoice_id, сумма, пациент_id_токен).                                                                     | Kafka topic
 4 | InvoiceEvent        | Message Queue -> Финтех                  | Финтех-приложение получает уведомление и извлекает необходимые поля.                                                                                   | Consumer group
 5 | ScoreRequest        | Финтех -> ИИ                             | Финтех-приложение вызывает Prediction API с feature-вектором (доход, история платежей, тип процедуры и т.д.) с токенизированными данными пользователя. | REST API
 6 | ScoreResponse       | ИИ -> Финтех                             | Возвращается скоринговый результат (0–1), вероятность одобрения.                                                                                       | API response 
 7 | CreditDecisionEvent | Финтех -> Message Queue                  | Финтех-приложение принимает решение (Approved/Denied) и публикует событие.                                                                             | Kafka topic
 8 | DecisionReceived    | Message Queue -> Медицина                | Медицинское приложение обновляет статус счёта (Paid by Credit / Denied) и уведомляет пациента.                                                         | Consumer group + REST API
 9 | Notification        | Медицина -> Пользователь (портал)        | Пользователь получает уведомление о результате.                                                                                                        | Push/Email/SMS API
 
### Безопасность и комплаенс в процессе 

Этап  | Механизм защиты                           | Реализация              
--------------|-------------------------------------------|----------------------------------
 1 | Аутентификация пользователя               | Аутентификация пользователя до выполнения действий в системе с использованием IdP
 3-7 | Токенизация ПдН                           |
 1, 2, 5, 9 | Авторизация доступа                       | Разрешение вызовов API на уровне API Gateway
 1, 2, 5, 9 | Аудит действий                            | Логирование API-вызовов
 1-9  | Шифрование данных при передаче и хранении | Шифрование Kafka topics и REST вызовов (TLS), данных в БД (TDE)

### Бизнес-эффект и преимущества
Показатель  | Было                                       | Стало              
--------------|--------------------------------------------|----------------------------------
Time-to-approve   | 1–2 дня (ручная проверка)                  | < 1 минута (автоматический скоринг)
Нагрузка на DWH | Высокая (через SQL ETL)                    | Нулевая — события идут напрямую между доменами
Изменение схемы данных | Требовало обновления DWH, ETL              | Только обновление схемы Data Product
Доступность данных | Периодическая со значительными задержками  | Потоковая (streaming)
Масштабирование | Централизованная система с узким местом    | Автономные подсистемы по доменам
